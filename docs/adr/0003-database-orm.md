# 0003. Database and ORM — PostgreSQL 17 + Drizzle

**Status:** Accepted
**Date:** 2026-05-14

## Context

We need durable storage for `lookups`, `lookup_events`, `providers` runtime state, and (later) `users` + `payments`. Workloads are mixed: small typed rows + large JSONB blobs (OSINT results); high read locality on `lookups (provider_id, query_hash)`. Live-progress fan-out is handled by Redis Streams, not the DB. Drizzle was named in PROMPT.md.

## Decision

- **Database:** PostgreSQL 17.
- **ORM:** Drizzle ORM **1.0.0-rc.2** (release candidate; first v1 line that PROMPT.md asked for) + drizzle-kit at the matching version for migrations. We deliberately track the rc / beta channel so we feed feedback into the v1 release rather than getting stuck on the 0.45.x EOL line.
- **Driver:** `postgres` (a.k.a. `postgres-js`) — faster than `pg`, simpler API, plays well with Drizzle.
- **Schema lives in `packages/db/src/schema/`**, one file per table.
- **Migrations** generated by drizzle-kit, committed under `packages/db/migrations/`. API runs migrations on boot via a one-shot script with a leader lock (or a separate `migrate` compose service).

## Consequences

**Good:**
- Postgres-first: JSONB for OSINT result blobs, partial indexes, range types, `LISTEN/NOTIFY` available if we want a free pub/sub later.
- Drizzle gives end-to-end TS types from schema → query → result without code generation.
- Migrations are SQL files committed to repo — easy to review and roll back.
- `postgres-js` outperforms `pg` and avoids `pg-pool` configuration noise.

**Bad:**
- Drizzle is younger than Prisma; some advanced query shapes (recursive CTEs, complex JSONB ops) require the `sql` escape hatch.
- drizzle-kit's migration diff occasionally needs manual cleanup for column reorderings.

## Alternatives considered

- **MySQL** — weaker JSONB story, smaller Node ecosystem, no `LISTEN/NOTIFY`.
- **Prisma** — slow startup, heavy generator step, more opinionated; runtime overhead.
- **Kysely** — pure query builder, no migration tool; we'd bolt on `dbmate` or similar.
- **Raw SQL + a thin client** — gives up the ergonomics with no benefit for this scale.

## Triggers to reconsider

- Drizzle blocks a query we need and the `sql` escape hatch becomes pervasive → consider mixing in Kysely.
- We need a managed Postgres with auto-failover → switch host (Hetzner Postgres, Supabase, Neon) without changing ORM.
- Multi-tenant row-level security gets complex → reconsider whether Drizzle's RLS support is enough.
